## Hermes + MCP restructure (design, 2026-10-22)

Goal: Hermes Agent (Nous Research) becomes the harness (browsing, judgment, retries, skills and memory), and everything deterministic moves into our own MCP server, which Hermes calls as tools. Aims: lower LLM cost, tighter security. The server must run over stdio (locally) and over HTTPS with authentication (remote, possibly behind Composio) with no code change between the two. The old pipeline (`python -m sonar.main`, keyword matching included) stays as it is and is the fallback until the Hermes version matches it.

**Where it lives:** same repo, new folder `src/sonar_mcp/` that imports the existing modules. Existing files are not changed in phase 1.

**Stays with Hermes (needs judgment):**
- reaching the list and sorting it newest first;
- recognizing the result rows;
- "load more" / "next";
- working out addresses for script-only links (Ontario);
- frames and folded groups (Ariba);
- retrying a browser step that went wrong.

**Moves to the MCP server (deterministic):**
- run lock, run records and cost caps;
- login (code only; Hermes never types passwords);
- cleaning the rows Hermes returns (hosts, normalization, job ID);
- stop rule, watermark and dedup;
- opening postings (pacing, title check, click fallback), extraction and storage;
- boilerplate stripping and Jev matching;
- summaries (a tool-less model call inside the server);
- report, email, route notes and screenshots.

The browser guards are not a tool: they stay network policy on the browser.

**Retired in the Hermes version:** `agent_runner.converse` and `browser(code)`, `code_check.py`, the browser-use CLI, the agent prompt parts of `navigation/dom.py`. Keyword matching is not exposed (it stays in the old pipeline).

**MCP tools** (narrow: no SQL, no settings/sites/keywords edits, no email recipient, no arbitrary fetch, no file access, no credentials):

| Tool | Inputs | Output |
| --- | --- | --- |
| `start_run` | sites?, days? | run_id; per site: name, start_url, hints, cutoff |
| `open_site` | run_id, site | browser ready, logged_in, tabs (launches the guarded browser, logs in with code) |
| `capture_list_rows` | run_id, site, link_filter?, frame_text? | rows_seen, new_rows, oldest/newest date, next = load_more or stop. The server reads the rows from the page itself, so Hermes never retypes them (about 70% of today's per-page cost) |
| `submit_list_rows` | run_id, site, rows [{title, url, date}], has_more | same as above (fallback; rows untrusted) |
| `collect_postings` | run_id, site | stored, skipped_known, failed_opens, watermark_moved |
| `save_route_note` | run_id, site, note (300 chars max) | saved, unchanged or ignored |
| `close_site` | run_id, site | closed |
| `match_site` (Jev) | run_id, site | scored, matches, needs_review, unscored |
| `summarize_matches` | run_id | written, failed, skipped_by_cap |
| `send_report` | run_id | report_written, emailed (recipient from settings only; once per run) |
| `finish_run` | run_id | status, per-site counts, cost |
| `run_status` | run_id | read-only counts and cost |

**Security layers:**
1. **Hermes uses only its named browser tools:** `browser_navigate`, `browser_snapshot`, `browser_click`, `browser_scroll`, `browser_back`. No Python mode (`browser_exec`): Hermes only offers it with the terminal on, and the terminal is a full shell. Terminal, file, code and web toolsets are off; `browser.restrict_evaluate: true`; never a cloud browser backend.
2. **A Hermes plugin with a `pre_tool_call` hook** (it replaces `code_check.py`):
   - allowlists tools;
   - checks `browser_navigate` hosts against the site's allowed hosts;
   - blocks `browser_type`, `browser_press`, `browser_console` and `browser_dialog`;
   - allows `browser_cdp` only for read-only methods;
   - blocks clicks on action-like elements (submit, apply, accept, register, log out, delete, bid, upload, plus French), using a `post_tool_call` hook that remembers what each snapshot ref was.

   Hermes hooks fail open, so the hook catches its own errors and blocks on error.
3. **Our Playwright guards (`guards.py`), unchanged.** Hermes attaches to our guarded Chromium with `browser.cdp_url`, exactly as the browser-use CLI does today, so every request still passes the guards.
4. **A network egress allowlist** around the container (site hosts plus OpenRouter). It catches what the guards cannot see, such as a new browser context opened over CDP, or a page script sending data to another host.
5. **Secret separation.** Hermes's process holds no site passwords and no SMTP password. The MCP server holds them and the database, as a separate OS user or container, so even a leaked shell finds little.

**Skills and memory:** on, so Hermes learns site routes and costs fall. Risk: a malicious page could make Hermes save lasting instructions. Recommended, not confirmed: new or changed skills go to a proposals folder that a person reviews, like hints today.

**Harness configuration lives in the repo (2026-10-22, developer's choice).** The Hermes settings (model, which tools are on or off, browser settings, the MCP server entry) are kept in one file, `config/hermes.yaml`, reviewed in pull requests. It holds no secrets (the OpenRouter key stays in `.env`). Hermes reads its config from a fixed place on disk, so at the start of each run Sonar copies the repo file there, replacing whatever is in that place; the developer never edits the installed copy. The spike checks whether Hermes can read the repo file directly with a flag, which would remove the copy step. A test fails if a dangerous tool (terminal, file, code, web) is turned on or `restrict_evaluate` is turned off. The Hermes model is set only in this file; the `navigation_model` entry in `settings.yaml` is retired in the Hermes version.

**OpenRouter:** one key for everything (Hermes, Jev, summaries) until there is a working product; `max_run_usd` then still covers the whole run. Hermes's model stays `openai/gpt-6.1-sol`.

**Private VM vs public server for Composio** (flagged, not chosen):
- **Transport and auth.**
  - Private VM: stdio, where Hermes starts the server as a child process with a minimal environment. No network, no auth.
  - Public server: streamable HTTP over TLS behind a reverse proxy, with bearer token or OAuth, Origin/Host checks, rate limits and size caps. The transport is chosen by configuration, never by a code change.
- **Where the browser lives.** In Composio mode Hermes needs our browser's CDP port, which must never be public. So the browser sits with Hermes, and the server tools that read from it (`capture_list_rows`, `collect_postings`) need a local helper or must receive the text.
- **Data.** Every tool input and output passes through Composio, so outputs stay counts and IDs, and logged-in pages never go through it.
- **Dangerous tools.** Anyone holding the token can trigger logins and email, so these need per-tool scope, idempotency (email sent once per run) and an audit log.
- **State.** HTTP sessions, possible concurrent and retried calls, and SQLite writes all need care.
- **Network.** Inbound 443 open, firewall rules, denial-of-service exposure.

The server therefore needs a narrow "advance the list" action that clicks the detected control itself (or returns the address when there is one). (2) On these two simple sites the start address is already the sorted list, so Hermes has almost nothing to decide; its value is on harder sites (Ontario: find the list and sort by clicking a header; Ariba: unfold a group inside a frame), where rows may also have no addresses of their own and the reader falls back to Hermes. Not yet tested: Ontario/Ariba shapes, frames, a second page, cards that are not table rows. (4) Still an estimate, not a measurement: per-page Hermes cost with this split (about 3 calls; corrected after the exact costs below: roughly $0.03 to $0.04, about the same as the old agent, not the $0.02 first written here). Measuring it needs the `mcp` Python package (new dependency, needs approval) and Hermes calls (a few cents).
- **Gateway finding (important for the design):** `hermes chat` does not run the agent in its own process. It sends the message to a background Hermes "gateway" process (`hermes_cli.main ... gateway run --quiet --idle-exit`) that the first call starts and later calls reuse. That process keeps the config, plugins and environment (including `SONAR_ALLOWED_HOSTS` and the API key) from when it started. I edited the config after it started, and the guard plugin silently did not apply: `browser_console` ran through the real command until I killed the process, then it was blocked. So Sonar must start Hermes itself in a known state (stop any old gateway, start a fresh one, confirm the guard plugin is loaded, then run), never rely on whatever is already running, and stop it at the end of the run. Same check as the plugin-fails-to-load finding above, just with a second way to hit it.
- **Test A (baseline, Hermes alone, five safe tools, guard ON, fresh gateway, identical prompt) on two sites, exact costs (2026-10-22, developer's go-ahead):** CanadaBuys: 7 model calls, 56 s, **$0.0755**, 14 rows read, 0 addresses (about 120,000 input tokens). - **Spike spend:** about $0.43 on the OpenRouter key since the second check-1 run, plus about $0.02 before it (all test runs; includes Hermes's hidden background calls such as session titles).
- **Spike conclusion so far (written before the `browser_exec` tests; where it conflicts with the "Hermes progression plan" section, that section wins):** the security story works (guards hold, hook blocks, `browser_exec` absent) but needs a start-up check that the guard is really loaded. The cost story does NOT show a saving: Hermes alone costs about 1.8x the old agent per page on both sites and returns less. Where the money goes: each Hermes call re-sends Hermes's own instructions (about 8,800 tokens) plus the page outline (about 4,400 tokens per snapshot), so one call costs roughly $0.01 before any real work, and a 7-call page costs about $0.07. Moving the row copying into our server would remove the extra calls and the outline re-reads, but at about 3 calls the page would still cost about $0.03 to $0.04, which is about the same as today, not a clear saving (an estimate; unmeasured). A saving would need Hermes's per-call overhead cut (fewer instructions, no hidden title call, caching) or a cheaper model. Next decision for the developer: continue to the MCP server and measure the real per-page cost with that in mind, or stop here and keep the old pipeline.
- **Cost-cutting rules proposed by the developer (2026-10-27):** (1) never call `browser_snapshot` right after `browser_navigate`, because navigate already returns the same outline; (2) snapshot only after a click, and only if Hermes needs to see the result; (3) if the next-page control has an address, `browser_navigate` to it instead of clicking, so no snapshot is needed either. Checked against the source: Hermes's own `browser_click` description says it "requires browser_navigate and browser_snapshot to be called first", which is why the model snapshots after navigating, so the rule must override it and should be enforced in the guard plugin (block a `browser_snapshot` when nothing changed since the last outline), not only in the prompt. `browser_navigate` takes only a `url` (no way to turn its outline off, so every page load still adds about 4,400 tokens that stay in the conversation); a click returns no outline. Caveat on rule 3: MERX's "Next" has a usable address (`?pageNumber=2`), but CanadaBuys's "Load more" link has an address that returns 403 when opened directly (decision 2026-10-09, not retested) and sits past Hermes's 15,000-character outline cut, so on CanadaBuys the server must do the click; the rule is "navigate to the address if there is one, else the server clicks it". Estimated effect: about 2 Hermes calls per list page, maybe about $0.02 per page (unmeasured; the growing outlines would raise later pages).

## Evaluation (summary)

- **Collection:** coverage against a hand count on one site; duplicate clicks; misclicks; run success rate. Compare both streams on the same window.
- **Extraction:** field accuracy on 20 to 30 listings checked against the live page.
- **Matching:** 50 to 100 listings labeled pursue/skip by decision-makers (30 double-labeled). Measure recall, precision, calibration, review-band size. Choose the threshold from the curve, biased toward recall (to confirm).
- **Summaries:** unsupported claims vs raw text, target zero.
- **Operations:** cost and time per listing and per run; failure rate by type.
- The labeled set doubles as a regression test before changing prompts, keywords, Jev questions or model versions.

## Failure handling (essentials)

- Every failure ends in: retry, skip and log, or stop the site and alert. Never a silently empty or wrong report.
- State lives in the database; steps are idempotent; a crashed run resumes.
- Session expired (redirect to login): re-login once, re-save, retry; then stop the site.
- 2FA or CAPTCHA: stop and alert a human. Account warning or restriction: stop the site immediately.
- A site returning zero listings is treated as a failure, not a quiet day.
- Rate limits: back off and lower concurrency. Site down: retry 3 times, then skip and note it in the report.
- Vision: seen ID after a click means close the tab; duplicate titles are disambiguated with a second visible detail; misclick retries once.
- DOM: normalize URLs; no ID in URL means fall back to title + client + posted date.
- Extraction: empty text means fall back to body text and flag the site; expand "Read more" first; store missing fields as null.
- Jev unavailable: mark listing unscored, never a non-match. Low confidence goes to a "needs review" section.
- Always send the email, even with zero matches, and list failed sites at the top.
- Cost cap per run; run lock per site; screenshot on navigation failure (built).

## Branching

- `main` is stable code only: what we can run in Docker for a demo. It changes only through a pull request from `dev`.
- `dev` is where work is combined and tested together. Never commit to it directly.
- One branch per build step, started from an up-to-date `dev`, named by type: `feat/keyword-matcher`, `feat/dom-navigator`, `fix/session-expiry`, `docs/readme`. Merge it into `dev` through a pull request once tests pass, then delete the branch.
- Promote `dev` to `main` often, after each finished piece of work, with a pull request and a normal merge commit (never squash, so the two branches keep one history). "Stable" means: the full test suite passes, and one supervised Docker run with email works.
- A hotfix for `main` starts from `main`; after it merges, merge `main` back into `dev` so they do not drift apart. Keep this rare.
- Mark demo-ready versions with tags on `main`: `demo-1-keywords`, `demo-2-jev`.
- Keyword vs Jev and vision vs DOM are config switches, not separate branches.
